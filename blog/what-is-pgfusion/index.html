pgfusion: zero-copy analytics on PostgreSQL

21st July, 2026
Database Postgres Arrow DataFusion

pgfusion runs analytical SQL directly on PostgreSQL's own data files — no ETL, no second copy. It reads PostgreSQL heap files from disk, converts them to Apache Arrow, and executes queries with DataFusion, a vectorized columnar query engine. You point it at a PostgreSQL data directory and query the live tables — no ingest pipeline, no replica-into-a-warehouse, no separate system to keep in sync.

The result: faster analytical queries than PostgreSQL itself on large tables (window functions, group-by aggregations, count(DISTINCT), time-series rollups), with PostgreSQL remaining the single source of truth.

TPC-H: the full 22-query benchmark

The clearest single picture is the standard TPC-H decision-support benchmark — all 22 analytical queries at scale factor 10 (~60M-row lineitem), run against both engines on the same machine and hardware.

pgfusion completed all 22 queries; PostgreSQL failed or timed out on 4 (Q2, Q17, Q20 did not complete; Q21 hit the 300 s timeout). Across the 18 queries both engines finished, pgfusion is 3.2× faster by geometric mean (17 wins, 1 loss) and 4.3× faster by total wall time (189 s vs 819 s).

The wins are biggest exactly where PostgreSQL's row-at-a-time execution hurts most — multi-way joins with heavy aggregation (Q9, Q18), count(DISTINCT) and grouped distinct work (Q16, Q22), and correlated / subquery-driven aggregates (Q13). The one loss (Q7) and the narrower wins are join-heavy shapes where DataFusion's plan isn't yet better than PostgreSQL's.

The win holds as the data grows. Take Q1 (the pricing-summary scan-and-aggregate) and grow the data 5× to SF50 (300M-row lineitem): pgfusion goes 9.2 s → 9.6 s and PostgreSQL 19.9 s → 21.7 s — both essentially flat (Q1's aggregate collapses to four output rows, so neither engine's sort/aggregate grows), and the ~2.2× pgfusion advantage is unchanged at the larger scale. Where pgfusion pulls further ahead is the memory-bound shapes — the external-sort and count(DISTINCT) queries — not this scan-bound one.

How it works, briefly

  • Reads heap files, not the wire protocol. pgfusion opens PostgreSQL's on-disk table files directly and parses the row-major page format itself, so it never goes through the PostgreSQL executor for the scan.

  • Transposes to columnar Arrow. Row-major heap tuples become columnar Arrow batches, which DataFusion processes vectorized (SIMD-friendly), the way a columnar analytical engine does.

  • No buffer pool or page cache of its own (yet). Unlike PostgreSQL's shared_buffers, pgfusion keeps no internal cache — it re-reads and re-decodes the heap files (from the OS page cache) on every query. This keeps it stateless and copy-free, but means it pays the full scan-and-transpose cost each run; an internal columnar cache is future work.

  • Consistency via snapshot (+ optional checkpoint). Reading files under a live writer needs care. pgfusion runs each query inside a REPEATABLE READ transaction (stable tuple visibility) so it reads a coherent MVCC snapshot rather than a dirty mid-write state. Where that snapshot connection points depends on whether you also checkpoint:

    • Snapshot only (recommended): connect to whichever server you're reading — including a read replica, which fully supports read-only REPEATABLE READ snapshots. No primary connection needed.
    • With CHECKPOINT (experimental): if you want pgfusion to flush dirty buffers to the heap files first, that CHECKPOINT must run on the primary (a replica can only do a bounded restartpoint). But a CHECKPOINT per query is expensive, and running it regularly against a busy primary causes real write-performance and I/O problems — so this is experimental, not a production setting.

    The proper fix — WAL integration, tracking changes incrementally with no per-query checkpoint at all — is in progress. Until then the snapshot-only path is the sensible one; it's best suited to data that isn't being continuously rewritten (snapshots, quiet tables, or a standby not under heavy write load — see below).

  • Speaks Arrow Flight SQL. A server mode exposes the engine over Flight SQL / ADBC, so any Arrow client (Python, Go, Java, DuckDB, …) can query it and get columnar results back, or use the CLI directly.

The core trade-off

pgfusion is a deliberate compromise. It gives up the peak performance of a native columnar store — one that keeps data column-major on disk with row-group / column pruning, zone maps, and compression — in exchange for needing no copy of the data at all. It reads PostgreSQL's row-major heap and transposes it on every scan, so it can't prune at the storage layer the way a native columnar format can, and it will never match a dedicated system on raw throughput.

So the honest positioning:

If your analytics justify a dedicated columnar database, use one. ClickHouse, DuckDB, or a Parquet-backed lakehouse will be faster for sustained production analytical workloads. pgfusion is for when the copy itself is the cost you want to avoid.

pgfusion complements PostgreSQL; it doesn't compete with ClickHouse.

Where pgfusion fits

Exploring data before building a pipeline. Before you commit to standing up a warehouse and an ETL pipeline, point pgfusion at your PostgreSQL data and actually run the analytical queries. Profile the data, prototype the dashboards, and decide whether a dedicated pipeline is even worth building — on live data, today, with no setup.

Zero-duplication analytics. When you can't or don't want a second copy of your PostgreSQL data — for freshness, operational simplicity, cost, or compliance / data-egress reasons — pgfusion gives you faster-than-PostgreSQL analytics in place, with one source of truth.

Offline / snapshot analysis. Query a pg_basebackup or a filesystem snapshot directly. The files are immutable, so consistency is free (no checkpoint needed) — analyze last night's backup without restoring it into a running PostgreSQL.

Small and mid-size teams without warehouse infrastructure. If your data and budget don't justify Snowflake/BigQuery/ClickHouse, pgfusion is a 2–3× analytical speedup on the PostgreSQL you already run — no new systems to operate.

Experimental / on the roadmap

A few directions that are promising but experimental — treat these as future work, not production-ready capabilities:

  • Promotable read-replica sidecar. Run pgfusion alongside a physical streaming standby. The standby stays a byte-identical PostgreSQL replica (still promotable for HA / failover), while pgfusion serves fast analytics off its heap files — one node doing both, instead of a separate analytical copy that can't be promoted. There is a working proof-of-concept (examples/replica-sidecar/) — primary + streaming standby + pgfusion sidecar, with a client that writes to the primary, watches it replicate, and runs analytics ~3× faster than PostgreSQL off the standby's files. But testing it surfaced the real limitation:

    • Reading a standby's files means reading only what has been flushed to disk. Under a live writer, recently-replayed rows sit in the standby's shared buffers, unflushed, so pgfusion's view lags the live standby — and under sustained writes the file view can even become non-contiguous (some pages flushed, others not), i.e. temporarily inconsistent, until the buffers flush. When the standby is quiescent, the view is a clean, current, consistent snapshot.
    • You cannot fully force a live standby to flush on demand. A standby CHECKPOINT is a bounded restartpoint; a primary CHECKPOINT propagates only asynchronously — and, as noted above, checkpointing per query is not a production-viable approach (it hurts the primary's write performance).

    So the sidecar is usable today for read-mostly or batch analytics against a standby that is not under heavy write load, and the general answer — a coherent, current view of a hot standby without any checkpoint — is exactly what WAL integration is meant to deliver.

  • Index-aware scans. Reuse PostgreSQL's own B-tree (and other) indexes to prune scans, which would close much of the gap on selective queries where PostgreSQL currently wins.

Status

pgfusion is early and evolving, and not yet fully PostgreSQL-compatible. Most analytical SQL works — the benchmark queries ran unmodified and returned results identical to PostgreSQL — but there are gaps in type coverage, functions, and edge-case semantics, and some queries won't parse or plan yet.

Real query feedback is what shapes it. Point it at your PostgreSQL data, run your analytical queries, and tell us what works and what doesn't — the failures are as useful as the speedups.
